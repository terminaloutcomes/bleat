# 10,000-book performance baseline

First-release performance baseline for spec section 19 / GitHub issue
[#46](https://github.com/terminaloutcomes/bleat/issues/46). Physical-device
energy evidence is tracked separately in
[GitHub issue #95](https://github.com/terminaloutcomes/bleat/issues/95).
Records dataset construction, device and OS/build, configuration, launch time,
memory, energy, storage, cache fallback, and observed responsiveness.

## Dataset construction

The cache stores whole serialized pages as JSON blobs in SwiftData
(`Sources/BleatCore/LibraryCache.swift`, `CachedLibraryPageRecord`), not
individual book rows. 10,000 books therefore equal 200 pages at limit 50
(host cache tests) or 500 pages at the app default limit of 20
(`App/AppModel.swift`, `makeLibraryItemsPageRequest`).

- Host cache dataset: 10,000 deterministic `LibraryBookSummary` records
  generated by `LibraryBookSummaryGenerator`
  (`Tests/BleatCoreTests/LibraryCachePerformanceTests.swift`), packed into
  200 `LibraryItemsPage` blobs at limit 50.
- App browsing dataset: 10,000 records paged through `AppModel` at limit 20
  via `TestAppService.pagedProvider`
  (`Tests/BleatAppTests/AppModelTests.swift`,
  `testTenKBooksLoadNextBooksPagePerformance`).
- Simulator browsing dataset: 10,000 records served by the
  `--ui-testing-large-library` scenario
  (`App/UITestAppService.swift`), routed through the real
  `AppModel` browsing path. The performance script compiles the fixture with
  `BLEAT_UI_TESTING`; ordinary Release builds exclude it.
- Live end-to-end dataset: `TestSupport/ServerHarness/generate-large-library.sh`
  generates 10,000 folders of ~1s silent mp3 + `metadata.json`; seeded into a
  disposable "Bleat Large Fixtures" library via
  `scripts/live-test-environment.sh`.

The generator's shell entry point launches `scripts`' Rust
`generate-large-library` binary and requires Cargo and ffmpeg. It preserves
`BLEAT_LARGE_LIBRARY_COUNT` (default 10000), the optional output directory,
and `BLEAT_REPOSITORY_ROOT`. Counts must be integers from 1 through 100000.
A new or empty destination, or one containing only the exact checked-in
`.gitignore` and empty `.gitkeep` scaffold from
`TestSupport/ServerHarness/media-large/`, is initialized with
`.bleat-large-library.json`. Scaffold files must be single-link regular files
with identical bytes; this exact identity is the scaffold recognition contract.
They are preserved without replacement or deletion. Any additional or changed
content prevents scaffold initialization. Other populated destinations without
a valid manifest are rejected without claiming or replacing their contents. Older unmarked datasets must be retained
and a new empty destination selected; do not add a marker to adopt old data.

Regeneration validates the manifest, each recorded book's exact two-file shape,
structurally decoded metadata and SHA-256 audio identity before replacing any
books. Audio hashes deliberately compare exact media bytes as the generated
resource ownership contract. Changed books, extra book contents, symlinks,
hard-linked files and unowned numeric-name collisions cause safe refusal.
Unrecorded siblings (including `book-notes` and `.silent-template.mp3`) survive.
A unique owned staging directory contains temporary media and is cleaned on
normal failures. A manifest lock rejects overlapping generator invocations.
Media generation finishes before old books are removed. Before publication,
the locked manifest is written and synchronized with a typed `publishing` state;
the directory is synchronized before replacing books. After all replacements,
the directory is synchronized before recording `ready`. Interrupted publication
therefore rejects every retry count, including the former or a smaller count,
and requires inspection rather than automatic recovery. Do not edit fixture contents while generation is running.

Focused ownership and wrapper regressions are in
`scripts/src/large_library.rs` and `scripts/tests/large_library_cli.rs`.
They use disposable directories and fixture audio; separately smoke-test the
shell entry point with real ffmpeg and small counts before using the live dataset.

### Generator ownership verification (2026-10-18)

The focused `large_library::tests` selection passed all seven cases, and the
`large_library_cli` integration target passed both cases. The complete
`mise exec -- cargo test --locked --package scripts --all-targets --all-features -- --test-threads=4`
gate passed 134 tests with no failures or ignored tests. Clippy with all targets,
all features and `-D warnings`, workspace formatting verification, and
`mise run docs:check` passed. Initial JSON/hash compilation errors were corrected;
an initial wrapper-test failure caused by personal zsh startup configuration was
resolved by isolating `ZDOTDIR` in that disposable test fixture.

A separate real-wrapper/ffmpeg smoke check generated 3, then 1, then 1 books in
a fresh disposable destination. Each run verified the exact generated names,
parsed metadata, valid 1-second MP3 audio, retained `book-notes` sentinel and
unowned template, and absence of staging leftovers. The disposable destination
was removed afterward. These are generator safety checks; the historical
10,000-book performance and live-server results below were not rerun.

### Follow-up review corrections (2026-10-18)

PR #381 follow-up review identified two P2 defects in the initial implementation:
the checked-in default-output scaffold was rejected, and interrupted expansion
could be accepted at the previous count while leaving extra books. Both were
reproduced by failing regressions before correction. The default wrapper test
now copies the actual checked-in scaffold; altered, augmented and symlinked
scaffolds are rejected without mutation. The
`rejects_interrupted_expansion_when_retry_uses_old_or_smaller_count` regression
interrupts the actual rename loop after an extra book is published, using
identical audio. Retries at the former, smaller and expanded counts all return
the typed interrupted-publication failure without changing retained resources.

After these corrections, all nine `large_library::tests` cases and both
`large_library_cli` cases passed. The same complete scripts gate passed 136 tests
with no failures or ignored tests; Clippy, formatting and documentation checks
passed. A new real-wrapper/ffmpeg 3 → 1 → 1 smoke run started from an exact copy
of the tracked scaffold and verified preserved scaffold/sentinels, exact book
names, parsed metadata, valid 1-second audio, `ready` manifest counts and staging
cleanup. Both reported P2 findings are resolved; interrupted publication still
requires inspection and fixture contents must remain unchanged during generation.

## Off-main-actor evidence

`LibraryCache` is a `@ModelActor actor` and `AudiobookshelfAPI` is an
`actor`; all page decode and persistence run off the main actor
(`Sources/BleatCore/LibraryCache.swift:396`,
`Sources/BleatCore/AudiobookshelfAPI.swift:422`). The regression test
`testCacheReadsDoNotBlockTheMainActor` synchronizes on the read workload
starting, then confirms a main-actor heartbeat keeps advancing while 200
cache reads are underway — proving the main actor stays responsive during
decode, not just before it begins.

Filtering and sorting are server-side: `LibraryItemsPageRequest.queryItems`
(`Sources/BleatCore/LibraryModels.swift:184`) emits query parameters and
the client performs no in-memory filter or sort. The `AudiobookshelfAPI`
actor decodes the filtered/sorted response off-main.

`AppModel.loadNextBooksPage` preserves account, library, filter, and
generation checks on `@MainActor`, then delegates growing page assembly and
de-duplication to `LibraryPageMerger`. Only the completed page is published
back to observable state. `AppModelTests.testTenKBooksLoadNextBooksPagePerformance`
confirms de-duplication, final pagination state, and main-actor heartbeat
progress while the full 10,000-book dataset loads through `AppModel`.
