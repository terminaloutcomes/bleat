# 10,000-book performance baseline

First-release performance baseline for spec section 19 / GitHub issue
[#46](https://github.com/terminaloutcomes/bleat/issues/46). Physical-device
energy evidence is tracked separately in
[GitHub issue #95](https://github.com/terminaloutcomes/bleat/issues/95).
Records dataset construction, device and OS/build, configuration, launch time,
memory, energy, storage, cache fallback, and observed responsiveness.

## Dataset construction

The cache stores whole serialized pages as JSON blobs in SwiftData
(`Sources/BleatCore/LibraryCache.swift`, `CachedLibraryPageRecord`), not
individual book rows. 10,000 books therefore equal 200 pages at limit 50
(host cache tests) or 500 pages at the app default limit of 20
(`App/AppModel.swift`, `makeLibraryItemsPageRequest`).

- Host cache dataset: 10,000 deterministic `LibraryBookSummary` records
  generated by `LibraryBookSummaryGenerator`
  (`Tests/BleatCoreTests/LibraryCachePerformanceTests.swift`), packed into
  200 `LibraryItemsPage` blobs at limit 50.
- App browsing dataset: 10,000 records paged through `AppModel` at limit 20
  via `TestAppService.pagedProvider`
  (`Tests/BleatAppTests/AppModelTests.swift`,
  `testTenKBooksLoadNextBooksPagePerformance`).
- Simulator browsing dataset: 10,000 records served by the
  `--ui-testing-large-library` scenario
  (`App/UITestAppService.swift`), routed through the real
  `AppModel` browsing path. The performance script compiles the fixture with
  `BLEAT_UI_TESTING`; ordinary Release builds exclude it.
- Live end-to-end dataset: `TestSupport/ServerHarness/generate-large-library.sh`
  generates 10,000 folders of ~1s silent mp3 + `metadata.json`; seeded into a
  disposable "Bleat Large Fixtures" library via
  `scripts/live-test-environment.sh`.

## Off-main-actor evidence

`LibraryCache` is a `@ModelActor actor` and `AudiobookshelfAPI` is an
`actor`; all page decode and persistence run off the main actor
(`Sources/BleatCore/LibraryCache.swift:396`,
`Sources/BleatCore/AudiobookshelfAPI.swift:422`). The regression test
`testCacheReadsDoNotBlockTheMainActor` synchronizes on the read workload
starting, then confirms a main-actor heartbeat keeps advancing while 200
cache reads are underway — proving the main actor stays responsive during
decode, not just before it begins.

Filtering and sorting are server-side: `LibraryItemsPageRequest.queryItems`
(`Sources/BleatCore/LibraryModels.swift:184`) emits query parameters and
the client performs no in-memory filter or sort. The `AudiobookshelfAPI`
actor decodes the filtered/sorted response off-main.

`AppModel.loadNextBooksPage` preserves account, library, filter, and
generation checks on `@MainActor`, then delegates growing page assembly and
de-duplication to `LibraryPageMerger`. Only the completed page is published
back to observable state. `AppModelTests.testTenKBooksLoadNextBooksPagePerformance`
confirms de-duplication, final pagination state, and main-actor heartbeat
progress while the full 10,000-book dataset loads through `AppModel`.
