# Tests outside core and app model

Tracked by [issue #362](https://github.com/terminaloutcomes/bleat/issues/362). Owner for these follow-ups: Bleat maintainers. `TestSupport/TestAudit/other.json` records source-specific cases and shared rule profiles; its pending count is authoritative for unreviewed bodies. No full-suite compliance or execution claim is made.

## Actionable follow-ups

1. **Verify exact identities in every runner.** `scripts/test-core.sh` checks that at least one test passed and that a target name occurs, but it does not compare the exact requested case set or reject duplicate case identities. `scripts/src/ci_smoke.rs` similarly requires more than two cases, a target, and the two named smoke cases but does not reject additional or duplicate cases. `scripts/test-live.sh` trusts `swift test --filter` exit status and does not inspect executed test identities/counts. `scripts/test-app-live.sh` checks that the online/offline `.xcresult` bundles exist, then checks proxy evidence, but does not verify each requested XCUITest case and outcome. Add an expected-ID verifier per runner (zero, missing, duplicate, unexpected, failed, and unexpected skipped case tests), preserve each runner's allowed-skip contract, and retain result artifacts. This is needed to distinguish a real passing selection from an empty, partial, or contaminated bundle.

2. **Verify bounded UI waits in Xcode.** `scrollUntilHittable` and related scroll/wait helpers in `Tests/BleatUITests` previously could exhaust their bounded polling loops without reporting a failure at the call site. The helpers now preserve their attempt bounds and call `XCTFail` with the caller's `file` and `line`; each caller still needs its semantic postcondition. An additional timing review added bounded playback-label waits before mini-player gestures and waits for the prior chapter row before tapping. These Swift changes were handed to the parent-owned Xcode validation; see the main audit record for its exact outcome.

3. **Replace elapsed-time inference for download completion with a completion condition.** `checkEditDuringDownload` (used by `testBookDetailEditSurvivesSameBookDownloadProgress` and `testBookDetailEditSurvivesUnrelatedDownloadProgress`) waits 42 seconds via `DispatchQueue.main.asyncAfter`, then treats that interval as “Download completes while editing.” The test checks that the editor and draft remain, but does not observe that the transfer reached its completed state. Preserve the progress-during-edit scenario and add a fixture completion signal or asserted completed-download state, with a bounded timeout. Until then, the check proves editor persistence during elapsed time, while transfer completion is only presumed.

4. **Assert a playback update during menu stability checks.** `testPlaybackRateMenuRemainsStableAcrossTimeUpdates` and `testPlaybackActionMenusRemainStableAcrossTimeUpdates` hold playback menus open for two seconds before checking visibility and hit testing. They do not verify that a playback time update occurred during that interval. Add a fixture-observable tick/update condition with a bounded wait, then assert the menu remains usable after that update.

5. **Document the live JWT refresh threshold.** `TelemetryRecoveryLiveTests.testExistingPipelineRefreshesJWTAndDrainsQueuedSpan` configures a 1,000 ms refresh window, sleeps 1,100 ms, then requests a token to exercise refresh. This is intentionally elapsed-time based and preserves real token/collector integration, but the 100 ms margin is not explained in the test. Record why that margin is adequate for the runner or expose a deterministic clock boundary while keeping at least one real-time integration case.

6. **Resolved: keep protected capacity occupied through the health probe.** On explicit user request, `bleat_api::http::tests::health_remains_available_while_protected_capacity_is_exhausted` now holds the handler on an entry/release gate. It verifies zero available permits before and after the health response, releases the handler before asserting, and verifies the permit is restored after completion. Both request futures are joined within a five-second failure budget; timeout cancels them without detached work. The one-second route deadline remains and cannot silently make the test pass, because the held-capacity and successful protected-response assertions would fail. Follow-up validation is recorded in the main audit.

7. **Constrain large-library generator cleanup.** `TestSupport/ServerHarness/generate-large-library.sh` removes `${output_dir}/book-*` before regenerating. Its default repository-owned `media-large` destination is scoped, but the optional output directory can point at an unrelated location. Validate the destination against a dedicated generated-fixture directory or require a clearly named marker before deleting generated folders.

8. **Use a native async lifecycle for API signing-key fixtures.** `bleat-api/tests/http_api.rs` writes signing-key fixtures with `std::fs::write` from async test code. `production_router` synchronously removes its generated key only after router construction succeeds; the malformed-key case synchronously removes its file only after the expected router error returns. An earlier setup or assertion failure can therefore block the executor or leave a file in the global temp directory. Bleat maintainers handling issue #362 should create the per-test fixture with Tokio filesystem operations and use an explicit async cleanup path that runs on both success and failure, checking cleanup errors before asserting the operation result. Do not rely on `TempDir` drop for cleanup in async code, because that performs synchronous filesystem work. The two affected cases currently retain their router-failure assertions; this follow-up tracks the fixture lifecycle and failure cleanup, not the typed failure coverage.

## Fixed during this audit

`testBookContextMenuDownloadRunsInBackground` and `testContextDownloadAndRemovalAreMutuallyExclusive` replaced the prior guessed 8-second context-download delay with a cancellation-aware `UITestContextDownloadGate`. The debug fixture exposes a release button only while preparation is pending; each journey asserts its context-menu state, navigates to Downloads, releases the gate explicitly, and then waits for the download row. This observes the pending-to-progress transition without sleeping for an assumed duration.

`AuthenticatedOtlpSpanExporterLiveTests.testExportsWithRealJWTOverOTLPHTTP` now registers awaited exporter shutdown in XCTest teardown before exporting, so assertion failures also release pipeline resources. The three directly changed UI cases, bounded Rust admission waits, socket exchange, and App Store Connect temporary-file cases have their `fixed` decisions and exact changed postconditions recorded in `TestSupport/TestAudit/other.json`. API signing-key fixtures remain tracked by follow-up 8.

## Shared live-test support inspection

`TestSupport/ServerHarness/download_fault_proxy.py` was inspected with the application-live runner. Its `FaultState` guards arm/reset, one-shot fault claiming, sequence numbers, and event snapshots with a lock; evidence records range/status/auth scheme and whether a query exists without retaining token values. It injects exactly one `401` for the first ranged download starting above byte zero, forwards other requests, and uses a finite 120-second upstream connection timeout. `scripts/test-app-live.sh` selects a free proxy port, polls its health endpoint with a 50-by-100ms bound, arms the fault once, checks the `401`/refresh/resume event order, then terminates the proxy during cleanup. The source has no direct standalone test target; its behavior is exercised by the app-live flow, whose exact XCUITest identity/outcome verification is tracked in the runner follow-up.

The ordinary live harness uses unique Compose project names in `scripts/test-live.sh`, profile manifests with exact Audiobookshelf versions and image digests, and resets only that project’s volumes before seeding three known media fixtures. `live-profile.sh` checks the profile/image/version relationship; Caddy serves root and prefixed routes with a locally generated CA, and the app-live runner installs that CA only into its disposable Simulator. The Keycloak OIDC fixture and large-library media are separate setup paths. The large-library generator removes only `book-*` children of its configured destination, which motivates follow-up 7. Audiobookshelf cleanup/fixture reset flows were reviewed from source but not run in this audit; the separate disposable PostgreSQL/telemetry gates were subsequently run as recorded below.
